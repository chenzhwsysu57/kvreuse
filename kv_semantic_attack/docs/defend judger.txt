### BACKGROUND ###
在multi-agent系统中，经常会遇到需要重新使用一段文本的情况。例如，agent client给出他的问题；那么agent solver需要读取这段给出解决方案；agent audit也需要读取给出的问题和对应的方案进行审计。这个时候，问题会被另外两个agent重复读取，如果能够直接把其对应的kv cache给到agent audit拼接而不是重新prefill就可以节省效率。

不失一般性，假设服务器处理两个请求a和b：
服务器接收到请求 prefix a + block + task a, 进行了prefill，并返回了response。此时服务器缓存 KV(block | prefix a),意思是在prefix a的前缀的block KV cache，此时的KV cache承受了来自prefix a的信息

随后服务器接收到请求prefix b + block + task b。服务器会首先prefill prefix b，然后拼接 KV(prefix b)与前面缓存的 KV(block | prefix a)，再继续对task b进行prefill。

因为block跳过了prefill，此时效率得到提高，TTFT（Time to First Token）大大降低。

然而由于因果注意力，block的KV 总是保存了prefix a的任务信息，如果prefix a和b的信息是冲突的，此时prefill会让task b回答的过程中信息混乱进而导致性能不稳定。
 
为了进一步研究这样的现象，我们构造一个攻防系统。
攻击者负责找到尽可能多样化的、让模型在reuse过程中犯错的题目；
防御者负责想出一条remedy让所有的攻击失效；
attack judger负责判断攻击是否成功
defender judger负责判断防御是否成功
执行系统负责组装测试和返回结果

总的来说这个攻防系统从攻击者发起攻击，它会构造需要用到block的任务a和b，然后将构造的任务交给执行系统执行如下四个任务
prefill(prefix a + block + question)
prefill(prefix b + block + question)
prefill(prefix a) + reuse (block | prefix b) + prefill(question | all previous)
prefill(prefix b) + reuse (block | prefix a) + prefill(question | all previous)
 
执行系统通过对比观察四种情况下的模型reasoning过程，可以得知任务a b和block是否不支持reuse。

如果攻击成功，则防御者开始发起remedy。此时执行系统把remedy拼接到question之前进行补救，然后判断remedy是否成功。
